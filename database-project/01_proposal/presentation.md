# 1차 발표 흐름·대본·예상 질의응답

**청약 의사결정 노트 · 약 10분 발표 + 약 5분 Q&A · v0.2**

발표는 [기획안](proposal.md)을 화면 공유하면서 진행할 수 있다. 아래 시간은 진행 목표이며 실제 발화 시간을 측정한 결과가 아니다. 리허설에서 시간을 확인하고, 상세 컬럼과 SQL 문법 설명은 질의응답으로 넘긴다. 현재 기획·API 실호출 표본 확인을 완료했으며 DB 적재·Next.js 앱은 향후 구현한다.

## 2. 발표 대본

### ① 0:00–0:45 · 프로젝트 소개

제가 기획한 프로젝트는 ‘청약 의사결정 노트’입니다. 아파트 청약을 준비하는 사용자가 공고를 찾고, 주택형의 가격과 일정을 비교한 뒤, 왜 그 공고에 관심을 갖게 되었는지 기록하는 웹 서비스입니다.

핵심은 비교의 근거를 남기는 것입니다. 같은 법정동에서 어떤 면적과 기간의 거래를 몇 건 비교했는지 확인하고, 그 결과와 자신의 판단을 함께 보관하도록 계획했습니다. 이번 발표에서는 문제와 비즈니스 모델, 예상 데이터베이스 구조, 그리고 앞으로 무엇을 검증하고 구현할지 설명하겠습니다.

### ② 0:45–2:00 · 해결하고자 하는 문제

사용자가 공고를 검토할 때는 여러 종류의 정보를 함께 봐야 합니다. 같은 공고에서도 주택형별 면적과 가격이 다르고, 일반공급과 특별공급의 물량도 나뉩니다. 여기에 접수 일정과 참고할 기존 거래까지 확인해야 합니다.

제가 해결하려는 문제는 세 가지입니다. 첫째, 서로 다른 단위의 데이터를 비교하기 쉽게 연결하는 것입니다. 둘째, 여러 공고를 검토하면서 생긴 판단과 자금 메모를 공고별로 정리하는 것입니다. 셋째, 나중에 값이나 조건이 바뀌어도 당시 어떤 근거를 사용했는지 확인하는 것입니다.

예를 들어 오늘 조회한 거래 중앙값과 한 달 전에 메모할 때의 중앙값이 다르다면, 숫자만 저장해서는 왜 달라졌는지 설명하기 어렵습니다. 따라서 조건과 포함 거래, 그때 사용한 값까지 보존하려고 합니다. 이러한 문제의 중요도와 사용 빈도는 이후 사용자 인터뷰로 확인할 계획이며, 현재는 문제 가설로 제시합니다.

### ③ 2:00–3:00 · 사용자와 비즈니스 모델

주요 사용자는 관악구와 인접한 서울 서남권에서 청약을 준비하는 개인입니다. 공고는 전국 일반 APT를 대상으로 조회하되, 거래 비교는 관악구·동작구·금천구 세 지역부터 시작합니다. 개인 프로젝트에 주당 5시간에서 8시간을 투자하는 조건을 고려해 수집과 주소 검증 범위를 제한했습니다.

비즈니스 모델은 부분 유료 구독을 가정했습니다. 공고 조회와 기본 비교, 관심 목록과 개인 노트는 무료입니다. 유료 가치는 비교 이력을 여러 시점에 걸쳐 보관하고, 자금 시나리오를 비교하거나 맞춤 일정 알림을 받는 데 있다고 생각합니다.

다만 실제 가격이나 지불 의사는 아직 검증하지 않았습니다. 이번 과제에서는 핵심 기능과 DB 설계를 구현하고, 결제 시스템은 범위에서 제외합니다. 사용자가 어떤 작업을 반복하고 어떤 기록을 필요로 하는지 확인한 뒤 수익 모델을 구체화하겠습니다.

### ④ 3:00–4:30 · 사용자 흐름과 핵심 기능

사용자의 흐름은 검색, 상세 확인, 비교, 기록, 결과 확인 순서입니다.

먼저 사용자는 관심 지역과 예산, 접수 일정으로 공고를 검색합니다. 여기서 예산은 주택형의 분양최고금액을 기준으로 적용합니다. 한 공고에 여러 주택형이 있으므로 공고의 대표 가격 하나만 보고 판단하지 않도록 합니다.

상세 화면에서는 주택형별 면적과 공급 물량, 일정과 원 공고 링크를 봅니다. 지역과 전용면적이 확인된 경우에는 같은 법정동에서 전용면적이 5퍼센트 이내로 비슷한 거래를 최근 12개월 범위에서 비교합니다. 중앙값뿐 아니라 건수와 실제 포함 거래 목록도 표시합니다.

그다음 회원은 관심 공고를 저장하고, 보유 현금과 본인이 예상한 추가 비용, 판단 이유를 기록합니다. 비교 근거도 저장할 수 있도록 설계했습니다. 접수 이후에는 공개 경쟁률과 제공되는 당첨가점을 연결합니다.

가격과 면적이 미확인된 경우에는 그 사유를 표시하고 직접 비교를 진행하지 않습니다. 거래가 0건인 경우와 아직 비교할 수 없는 경우도 구분합니다. 청약자격이나 당첨확률을 자동 확정하는 기능은 포함하지 않습니다.

### ⑤ 4:30–5:40 · 데이터 출처와 검증할 부분

공공 API는 네 개를 사용합니다. 청약홈 분양정보에서 공고와 주택형을, 경쟁률 서비스에서 접수 결과를 가져옵니다. 국토교통부 아파트 매매 실거래가 상세 자료를 비교 거래로 사용하고, 행정안전부 법정동코드를 지역 연결의 기준으로 삼습니다. 과거 공고의 초기 적재에는 공식 CSV를 활용할 계획입니다.

네 서비스의 개발계정 신청과 승인을 확인하고, TypeScript 스크립트로 실제 호출했습니다. 공고 20건과 표본 한 공고의 주택형 5개·접수 결과, 세 구의 2026년 8월 거래 349건을 확인했습니다. 거래는 전체 페이지와 공식 법정동 코드도 대조했습니다. 다만 주택형의 전용면적 근거는 아직 미확인입니다. 응답의 공급면적을 실거래 전용면적과 그대로 비교하지 않겠습니다.

외부 식별자와 거래 취소·정정 표현도 확인할 예정입니다. VWorld 지오코더는 공식 문서의 응답 저장 제한 때문에 좌표 적재에서 제외했습니다. 따라서 처음에는 같은 법정동의 참고 거래라는 범위를 정확히 표시하고, 거리 비교는 별도로 확장하겠습니다.

### ⑥ 5:40–7:40 · 예상 테이블과 ERD

현재 예상 테이블은 15개이며, 다섯 가지 업무로 나눌 수 있습니다.

첫 번째는 공고와 공급, 접수 결과입니다. 하나의 공고에는 여러 주택형이 있고, 주택형에는 여러 공급유형이 있으므로 1:N 관계입니다. 경쟁률과 가점은 서로 다른 측정값이라 별도 관측 테이블로 구분했습니다. 결과는 수집 시점에 따라 달라질 수 있으므로 관측 이력을 보관합니다.

두 번째는 지역, 주소 매칭, 매매 거래입니다. 주소 매칭을 별도 테이블로 둔 이유는 매칭 실패와 수정 근거를 기록하기 위해서입니다. 실거래는 공고의 자식 데이터가 아니라 별개의 거래 사실로 저장합니다.

세 번째는 사용자와 관심 목록, 노트입니다. 한 회원이 여러 공고를 저장하고 여러 회원도 같은 공고를 저장하므로 사용자와 공고는 N:M입니다. 이 관계를 관심 목록 테이블로 해소하고, 하나의 관심 공고에 여러 노트를 연결했습니다.

네 번째는 비교 세트와 포함 거래입니다. 한 비교에는 여러 거래가 포함되고 같은 거래도 여러 비교에 사용되므로 여기에도 연결 테이블이 필요합니다. 비교 조건과 당시 주택형 가격은 비교 세트에, 거래의 당시 가격과 면적은 포함 거래에 보관합니다.

마지막은 수집 실행과 원본 기록입니다. 수집 실패를 운영자가 확인하고, 정규화 과정에서 잘못 해석한 자료를 다시 처리하기 위한 테이블입니다. 각 테이블은 저장하는 사실의 단위와 실제 사용할 기능을 기준으로 제안했고, 표본 확인에 따라 수정할 수 있습니다.

**화면 설명:** ERD에서 공고→주택형→공급을 먼저 가리킨다. 이어 사용자→관심 목록→공고, 비교 세트→포함 거래→실거래의 두 N:M 경로를 보여준다. 원본 출처의 점선은 마지막에 짧게 설명한다.

### ⑦ 7:40–9:00 · 데이터베이스 개념의 실제 적용

정규화는 반복되는 정보와 수정 문제를 줄이는 방향으로 적용하겠습니다. 예를 들어 공고의 이름과 일정을 주택형마다 복사하면 날짜가 바뀌었을 때 여러 행을 수정해야 합니다. 공고는 한 곳에 두고 주택형이 FK로 참조하도록 했습니다.

외부 번호는 원천 연결용 고유키 후보로 보존하고, 테이블 간 연결은 내부 PK와 FK를 사용합니다. 회원과 공고의 조합에는 고유 제약을 두어 관심 목록의 중복 저장을 막고, 미제공 데이터는 0과 구분하여 NULL로 처리합니다.

대표 SQL은 예산에 맞는 접수 예정 주택형을 JOIN으로 찾고, 지역·면적·기간에 맞는 거래의 건수와 중앙값을 함께 반환하는 질의입니다. 공급 물량은 GROUP BY로 집계하고, 아직 관심 목록에 없는 공고는 NOT EXISTS로 찾을 수 있습니다.

인덱스는 거래의 지역·기간·면적 검색 조건을 기준으로 후보를 정하고 실행계획으로 검증하겠습니다. 비교 저장에는 트랜잭션을 사용합니다. 비교 세트만 저장되고 포함 거래가 빠지는 상태를 막기 위해 모두 저장하거나, 오류 시 모두 롤백하도록 구현할 계획입니다.

### ⑧ 9:00–10:00 · 구현 계획과 완료 기준

1차에서는 기획안과 ERD 초안, 실제 API 표본 확인을 준비했습니다. 구현은 Next.js 풀스택과 TypeScript, PostgreSQL로 진행하고 검증한 서버 API 모듈을 재사용하겠습니다. 2차에는 화면 흐름과 요구사항을 구체화하고 초기 적재와 검색, 상세, 개인 기록 기능을 구현합니다. 3차에는 최종 명세와 정규화 근거, 주요 SQL과 인덱스, 트랜잭션을 검증합니다. 마지막 발표에서는 통합 앱과 변경 과정을 설명하겠습니다.

완료 여부는 구체적인 시연 장면으로 확인하려고 합니다. 여러 주택형이 정확히 연결되는지, 비교 조건과 실제 거래 목록을 확인할 수 있는지, 회원별 기록이 유지되는지, 비교 저장 오류가 롤백되는지, API 실패 시 정상 데이터가 남는지를 보여주겠습니다.

실제 API 표본 호출과 파서·페이지 처리 테스트는 완료했지만 DB와 앱의 성능·무결성·트랜잭션 검증은 남아 있습니다. 확인한 데이터와 피드백을 설계 변경 이력에 남기면서 프로젝트를 발전시키겠습니다.

## 3. 예상 질의응답

| 질문 | 답변의 핵심 |
|---|---|
| 공고와 주택형을 왜 분리했나요? | 공고의 이름·주소·일정은 공고 단위이고 면적·가격은 모델 단위입니다. 공고 정보를 반복 저장하면 수정 누락과 불일치가 생겨 FK로 연결했습니다. |
| 공급 물량을 별도 테이블로 둔 이유는 무엇인가요? | 주택형에 여러 공급 세부유형이 반복됩니다. 유형별 행으로 표현하면 유형별 검색·집계가 가능합니다. 특별공급 합계와 세부 항목을 함께 더하지 않도록 원본 총계를 대조합니다. |
| 어떤 N:M 관계가 있나요? | 사용자–공고는 `watchlist`, 비교 세트–거래는 `comparison_trade`로 해소합니다. 한 회원은 여러 공고를, 한 공고는 여러 회원을 가질 수 있습니다. 거래도 여러 비교에 포함될 수 있습니다. |
| 공고명이나 단지명을 PK로 사용하면 안 되나요? | 이름은 같거나 바뀔 수 있습니다. 내부 PK를 사용하고 원천 식별자를 별도 고유키 후보로 보존합니다. 거래의 고유키도 단지명만으로 정하지 않습니다. |
| 주택관리번호 하나면 충분하지 않나요? | 공고번호와 정정·재공고의 관계를 실제 응답에서 확인해야 합니다. 현재는 원천·주택관리번호·공고번호 조합을 후보로 제안하며, 검증 전 충분하다고 단정하지 않습니다. |
| FK가 없으면 어떤 문제가 생기나요? | 없는 공고의 주택형이나 없는 회원의 관심 목록, 없는 비교의 포함 거래가 생길 수 있습니다. FK로 참조 존재를 강제하고 적재·삭제 순서를 관리합니다. |
| 주소 매칭 테이블은 꼭 필요한가요? | 주소가 법정동으로 확인되지 않는 경우와 수정되는 경우를 관리해야 합니다. 원문·매칭 방법·시각·실패 이유를 남기고 현재 결과만 선택하는 기능에 사용합니다. |
| 공급지역코드로 거래와 조인하면 안 되나요? | 청약홈 공급지역코드와 실거래 조회용 법정동코드는 서로 다른 기준입니다. 공고 주소를 법정동으로 확인하여 연결합니다. 실제 코드 체계는 표본으로 검증합니다. |
| 주변 거래인데 거리를 사용하지 않나요? | 첫 버전의 표현은 같은 법정동의 참고 거래입니다. 거리나 도보 시간을 뜻하지 않습니다. 저장 가능한 좌표 출처를 확보한 뒤 거리 비교를 확장합니다. |
| 왜 평균보다 중앙값을 사용하나요? | 중앙값은 선택한 표본에서 일부 큰 값의 영향을 줄이는 참고 통계입니다. 표본의 질을 보장하지는 않으므로 건수·기간·포함 거래와 단지 속성도 함께 보여줍니다. |
| ±5%와 12개월은 어떤 근거로 정했나요? | 비교 조건을 명시하기 위한 초기 기본값입니다. 최적 조건으로 검증한 값은 아닙니다. 표본 수와 조건별 결과를 확인하고 변경 시 이유와 버전을 기록하겠습니다. |
| 전용면적이 없으면 어떻게 하나요? | 직접 비교를 중단하고 미확인 사유를 표시합니다. 공급면적이나 주택형 문자열의 숫자를 근거 없이 전용면적으로 대체하지 않습니다. |
| 거래가 적거나 0건이면요? | 건수와 조건을 공개하며 0건의 중앙값은 없음으로 표시합니다. 미검증과 0건을 구분하고 지역·면적·기간을 자동으로 확대하지 않습니다. |
| 취소 거래와 중복 거래는 어떻게 처리하나요? | 취소로 확인된 거래는 현재 비교에서 제외합니다. 같은 날짜·가격의 별개 거래도 있을 수 있어 그 값들의 해시로 무조건 삭제하지 않습니다. 공식 식별자와 정정·취소 표현을 검증한 뒤 규칙을 확정합니다. |
| 경쟁률과 당첨가점 테이블을 합치면 안 되나요? | 경쟁률은 공급수·신청수·비율, 가점은 점수 분포입니다. 의미와 제공 시점·결과 구분이 달라 분리했으며, 실제 응답에 따라 관계와 고유키를 보완합니다. |
| 현재 값과 비교 당시 값을 같이 저장하면 정규화 위반 아닌가요? | 현재 거래와 특정 비교에 사용한 과거 값은 시점과 사실의 단위가 다릅니다. 포함 거래의 복합키에 당시 값이 종속됩니다. 최종 설계에서 함수적 종속성을 확인하며, 단순 캐시와 구분합니다. |
| 인덱스를 왜 지역·기간·면적에 만드나요? | 대표 질의가 지역을 일치시키고 날짜와 면적 범위로 거래를 찾기 때문입니다. 실제 분포와 실행계획을 보고 순서·효과를 판단하며 모든 컬럼에 인덱스를 만들지 않습니다. |
| 어떤 기능에 트랜잭션이 필요한가요? | 비교 세트와 포함 거래·당시 값을 함께 저장하는 기능입니다. 일부만 저장되면 판단 근거가 불완전해지므로 하나의 트랜잭션으로 처리하고 오류 시 롤백합니다. |
| API가 실패하거나 같은 자료를 다시 수집하면요? | 실패는 수집 실행에 기록하고 기존 정상 데이터를 유지합니다. 정상 응답의 반복 적재는 원천 키와 검증한 식별 규칙으로 업무 중복을 막습니다. 결과의 변경된 관측은 보존합니다. |
| 단순 조회 서비스와 어떤 차이가 있나요? | 사용자의 관심·노트·비교 이력이 업무 데이터로 누적됩니다. 조회 결과가 어떤 거래와 조건으로 만들어졌는지 확인하고, 저장 당시의 판단을 다시 설명하는 데 초점을 둡니다. |
| 정말 유료로 쓸 사람이 있을까요? | 아직 검증하지 않은 사업 가설입니다. 데이터 자체가 아니라 반복적인 기록·시나리오·일정 관리의 가치에 지불 의사가 있는지 인터뷰로 확인하겠습니다. 가격·수익을 확정하지 않았습니다. |
| 15개 테이블이 과도하지 않나요? | 각 테이블은 공고·모델·공급유형·관측·거래·관심·비교·수집 등 저장 단위가 다릅니다. 사용자 기능과 원본 재처리에 사용하며, 표본 검증 결과에 따라 불필요한 분리를 줄일 수 있습니다. |
| 지금 실제로 확인한 것은 무엇인가요? | API 네 개 승인과 실제 응답을 확인했습니다. 공고 20건·연결 모델 5개·접수 결과·세 구 한 달 거래 349건이며, 키·단위·페이지·공식 법정동을 대조했습니다. 타입 검사와 파서 등 단위 테스트 11개도 통과했습니다. CSV 파일 파싱·DB·Next.js 앱·12개월 비교·성능 검증은 아직 수행하지 않았습니다. |

## 4. 리허설과 제출 전 확인

- [ ] 기획안의 필수 7개 항목을 약 10분에 설명한다. 타이머로 실제 시간을 기록한다.
- [ ] 테이블 15개를 모두 읽는 대신 저장 단위와 두 N:M 경로를 ERD에서 설명한다.
- [ ] 공급면적/전용면적, 최고 분양금액/총 취득비용, 참고 통계/예측을 구분한다.
- [ ] 아직 검증하지 않은 키·단위·취소 처리·성능을 완료한 사실처럼 설명하지 않는다.
- [ ] 각 질문에 먼저 설계 이유를 답하고 필요할 때 표나 SQL을 보여준다.
- [ ] ERD 확대본과 API 검증 부록을 로컬에 준비하여 Zoom 화면 공유에서 읽을 수 있는지 확인한다.
- [ ] 제출 문서에 이름·학번 등 수업이 별도로 요구하는 정보가 있다면 제출 전에 추가한다.
- [ ] GitHub 업로드 이후 로그아웃 상태로 제출 URL, 링크와 이미지가 정상적으로 열리는지 확인한다.
