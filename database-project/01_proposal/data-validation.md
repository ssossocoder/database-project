# 공공데이터 활용신청·검증 부록

**청약 의사결정 노트 · 1차 기획안 v0.2 · 실제 호출 확인일 2026-09-29**

이 부록은 공식 자료에서 확인한 내용과 실제 응답 검증을 구분한다. 2026년 9월 29일 네 서비스의 개발계정 활용신청·승인을 확인하고 실제 표본 호출을 완료했다. 인증키는 루트와 향후 Next.js 앱 디렉터리의 로컬 `.env`에 설정했으며 Git에서 제외한다. CSV 다운로드·파싱, DB 적재, 12개월 전체 수집과 Next.js 화면 구현은 아직 수행하지 않았다.

## 1. 활용신청한 API

공공데이터포털에서 아래 **4개 서비스 각각** 개발계정 활용신청을 완료했다. 신청 목적은 대학교 DB 프로젝트의 웹 서비스 개발·API 표본 검증으로 작성했다.

> 대학교 데이터베이스 수업 프로젝트: 아파트 청약 공고와 매매 실거래 자료를 연계하여 가격·일정·비교 근거와 개인 의사결정 노트를 제공하는 웹 서비스의 설계 및 구현.

|---|---|---|---|
| 1 | [한국부동산원_청약홈 분양정보 조회 서비스](https://www.data.go.kr/data/15098547/openapi.do) | APT 공고 상세와 주택형별 상세. 다른 공급 종류는 초기 범위에서 제외 | 개발 승인 · 공고 20건·주택형 5개 정상 응답 |

이미 발급된 개인 공통 인증키를 사용했다. 서비스마다 키를 새로 발급한 것은 아니며, 같은 키의 활용 권한을 각각 신청했다. 승인 직후 포털은 호출 권한 반영에 보통 1~2시간, 일부 API는 최대 24시간이 걸릴 수 있다고 안내했다. 이번 실행에서는 네 서비스 모두 실제 정상 응답까지 확인했다.

키는 서버 환경변수에만 설정하고 문서·발표 자료·원본 파일명·GitHub에 포함하지 않는다. 요청 URL·오류 로그·로컬 원본을 저장할 때에도 키를 제거한다. 현재 TypeScript 호출 모듈과 독립 검증 명령이 있으며 예약 실행·DB 동기화는 향후 구현한다. [설정·실행 방법](../app/README.md)

청약홈 두 서비스는 개발단계 자동승인·운영단계 심의승인, 실거래 상세 서비스는 개발·운영단계 자동승인으로 안내된다. 포털의 신청 가능 트래픽은 청약홈 각 40,000, 실거래 상세 10,000으로 확인했다. 실제 할당량과 호출 제한은 승인 계정에서 재확인한다. [분양정보 이용조건](https://www.data.go.kr/data/15098547/openapi.do), [경쟁률 이용조건](https://www.data.go.kr/data/15098905/openapi.do), [실거래 상세 이용조건](https://www.data.go.kr/data/15126468/openapi.do)

## 3. 문서 확인 결과와 미확인 사항

아래 첫 표는 포털·CSV 항목에서 도출한 설계 검증 과제다. 실제 응답에서 확인한 영문 필드와 표본 결과는 이어지는 별도 표 및 5절에 기록했다. 표본 확인을 전체 사례의 검증으로 확대하지 않는다.

| 데이터·항목 | 문서에서 확인한 사실 | 예상 DB 처리 | 실제로 확인해야 할 점 |
|---|---|---|---|
| 공고 식별자 | 공고·주택형 CSV에 주택관리번호·공고번호가 있고 주택관리번호로 연결하도록 안내 | 공고 내부 PK와 외부 고유키를 분리; 식별자는 문자열 보존 | API 응답의 키 조합, 정정 공고 관계, 번호의 누락·재사용 여부 |
| 모델·주택형 | 주택형 CSV에 모델번호·주택형 항목 존재 | 공고 FK와 모델번호로 주택형 구분 | 모델번호의 앞자리·길이, 주택형 이름의 의미, CSV와 API 연결 |
| 면적 | 주택형 CSV 항목은 주택공급면적 | `supply_area_m2`와 확인된 `exclusive_area_m2`를 분리 | API·원 공고의 전용면적 근거. 주택형 문자열의 숫자만 보고 전용면적으로 확정하지 않음 |
| 가격 | 주택형 CSV의 분양최고금액 단위는 만원 | 원 단위 `max_price_won`으로 변환, 원문 보존 | API의 동일 단위 여부, 쉼표·공백·미제공 값, 최고금액 의미 |
| 공급 물량 | 일반·특별공급과 특별공급 세부유형 항목 존재 | 주택형–공급유형별 행으로 정리 | 총계와 세부항목 합계, 미제공과 실제 0의 구분 |
| 경쟁률 | 포털은 접수 건수의 사후 변경 가능성을 안내 | 값과 수집 시각을 관측 이력으로 보존 | 공급유형·순위·거주지역 구분, 신청수·경쟁률의 빈 값 표현과 고유키 |
| 당첨가점 | 기관 게시글은 APT 당첨가점 조회 기능을 안내 | 경쟁률과 별도 가점 관측에 저장 | 최소·최대·평균 값과 결과 구분의 실제 제공 여부·형식 |
| 매매 거래 조회 | 법정동 앞 5자리와 계약년월 6자리로 조회; XML 응답 | 지역·월별 수집과 전용면적·원 단위 가격 정리 | 필드명, 반환 금액 단위, 페이지 수, 거래 식별자·취소·정정 필드 |

### 실제 명세·응답에서 확인한 필드

| 대상 | 실제 확인 내용 | DB·코드 반영 |
|---|---|---|
| 일반 APT | `HOUSE_SECD = "01"`; 공고의 `HOUSE_MANAGE_NO`, `PBLANC_NO`; 표본 20개의 키 중복 없음 | 사전청약 `09`·신혼희망타운 `10`을 초기 조회에서 제외. 식별자 문자열 보존 |
| 연결 주택형 | 같은 공고 키의 `MODEL_NO` 5개; 앞자리 `01` 보존 | 내부 PK와 별도로 공고 FK + 모델번호 고유성 검토 |
| 면적·가격 | 명세의 `SUPLY_AR`는 공급면적, `LTTOT_TOP_AMOUNT`는 만원. 한 모델은 공급면적 112.7105, 분양최고금액을 원으로 바꾸면 589,300,000 | 전용면적은 `null`·미확인으로 남김. 금액은 bigint 정밀도로 변환해 문자열 반환 |
| 경쟁률 | `MODEL_NO`, `SUBSCRPT_RANK_CODE`, `RESIDE_SECD`, `REQ_CNT`, `CMPET_RATE` | 공고·모델·순위·거주지역의 단위를 보존. 표본 거주코드는 `01`, `02` |
| 당첨가점 | `MODEL_NO`, `RESIDE_SECD`, `LWET_SCORE`, `TOP_SCORE`, `AVRG_SCORE` | 경쟁률과 별도 스냅샷; 공고·모델·거주지역으로 연결 |
| 특별공급 | `HOUSE_TY`와 유형별 배정·접수 필드; **`MODEL_NO` 없음** | 표본 5행은 공고 안에서 `HOUSE_TY`가 모델 1개와 일치. 이름이 중복·미일치하면 자동 연결하지 않음 |
| 페이지 건수 | 청약홈 `totalCount`는 필터 전 전체, `matchCount`는 조건에 맞는 전체 | 전체 페이지 판정에 `matchCount` 사용. 공고 20건은 표본으로 표시 |
| 실거래 | `dealAmount` 만원, `excluUseAr` 전용면적, `sggCd` 5자리·`umdCd` 5자리, `cdealType`·`cdealDay` | 공급면적과 분리; 법정동 10자리로 연결하고 공식 법정동 목록과 대조 |
| 거래 식별·취소 | `aptSeq`는 단지 일련번호. 349건 중 해제 표시 7건 관측 | 거래 ID로 사용하지 않음. 취소·미표시·필드 미제공을 구분하고 실제 복수 거래를 삭제하지 않음 |
| 정상·오류 | 청약홈 JSON, 실거래 XML의 정상 `resultCode = "000"`, 법정동 JSON의 `INFO-0` | HTTP 성공만으로 정상 판정하지 않음. 인증 오류 XML·빈 결과·금액 정밀도 등은 별도 단위 테스트 |

## 4. 표본 검증 순서

### V1. 공고 10~20건과 연결된 주택형

1. 인증 성공 여부, 전체 건수·페이지·오류 응답 구조를 확인한다.
2. 일반 APT의 구분 코드를 확인하여 사전청약 등 다른 유형을 제외한다.
3. 공고의 외부 식별자·이름·원문 주소·공고일·접수 일정·원 공고 링크를 확인한다.
4. 한 공고에 여러 주택형이 연결되는 사례를 확보하고 공고 키·모델 키를 대조한다.
5. 면적·가격·공급수의 원문과 정리한 값을 나란히 확인한다. 전용면적을 확인한 근거는 출처와 확인 시각을 남긴다.

전국 표본과 비교 지역의 과거 표본을 구분한다. 관악구·동작구·금천구에 현재 예정 공고가 없다면 그 사실을 기록하고, 시연용 과거 실제 공고는 과거 일정으로 명확히 표시한다.

### V2. 접수 완료 공고의 결과

1. V1에서 확인한 접수 완료 공고와 모델을 선택한다.
2. 일반공급 경쟁률·특별공급 신청현황·당첨가점을 각각 호출하여 실제 반환 단위를 확인한다.
3. 같은 모델이라도 순위·거주지역·공급유형이 다른 행을 합치지 않는지 점검한다.
4. 원천 제공 경쟁률을 우선 보존하고, 별도 계산값을 확인할 경우 분모의 의미와 0을 점검한다.
5. 이후 같은 범위를 다시 수집하여 값 변경 여부를 기록한다. 실제 변경이 없으면 “변경 없음”으로 기록하고 변경 사례를 꾸미지 않는다.

### V3. 지역·주소 매칭

1. 법정동 자료에서 서울 관악구·동작구·금천구의 시군구와 하위 법정동을 확인한다.
2. 공고의 원문 주소에서 지역을 확인하고 매칭 방법·결과·실패 이유를 기록한다.
3. 동 이름만 같은 다른 지역, 행정동/법정동 차이, 번지·도로명과 부지 설명이 섞인 주소를 점검한다.
4. 확인되지 않은 공고의 지역을 추정하여 직접 비교에 사용하지 않는다.

법정동코드 API는 주소를 자동으로 해석해 주는 지오코더가 아니다. 초기에는 표준 명칭과 원 공고 확인으로 지역을 연결하고 모호한 경우를 검토한다. VWorld는 공식 문서의 응답 저장 제한 때문에 좌표 영구 적재에 사용하지 않는다. 거리 기반 비교는 저장 가능한 출처를 확보한 후 확장한다. [VWorld 지오코더 문서](https://www.vworld.kr/dev/v4dv_geocoderguide2_s001.do)

### V4. 선택 지역의 월별 매매 거래

1. 먼저 3개 시군구 각 1개월을 호출해 XML 정상·오류 응답, 페이지, 단위와 필수 필드를 확인한다.
2. 페이지 전체를 조회한 후 총 건수와 파싱한 건수를 대조한다. 첫 페이지만 보고 그 달 전체 거래로 간주하지 않는다.
3. 취소·정정 필드와 공식 거래 식별자 유무를 확인한다. 같은 조건의 실제 복수 거래를 해시만으로 삭제하지 않는다.
4. 본 적재 단계에서는 기준일의 현재 월을 포함하여 직전 12개월 범위에 걸치는 모든 계약월을 조회한다. 날짜 기준 12개월은 월에 따라 13개의 계약월에 걸칠 수 있으므로 날짜로 마지막 필터를 적용한다.
5. 같은 법정동·전용면적 ±5%·기준일 이전 12개월 조건으로 거래 목록·건수·중앙값을 대조한다.

늦은 신고와 정정으로 과거 계약월의 응답도 바뀔 수 있으므로 재수집 범위는 실제 응답·API 제한을 확인해 정한다. 계약일이 과거라는 이유만으로 해당 거래가 당시 이미 공개되어 있었다고 해석하지 않는다.

### V5. CSV 초기 적재와 API 갱신

CSV 파일의 인코딩·헤더·행 수·빈 값·키 연결을 확인한다. 초기 공고와 주택형을 채운 뒤 최신 API로 갱신한다. API에서 관측한 최신 상태와 예전 CSV가 충돌하면 출처·관측 시점을 남겨 검토하고, 오래된 파일이 최신 업무 데이터를 덮어쓰지 않게 한다.

## 6. 구현 단계의 실패·경계값 확인

| 시나리오 | 기대 동작 |
|---|---|
| 인증·호출 제한·타임아웃·XML 오류 | 수집 실패로 기록하고 마지막 정상 데이터 유지; 빈 데이터로 덮어쓰지 않음 |
| 일부 페이지나 주택형 수집 실패 | 누락을 성공으로 표시하지 않고 완료 범위와 실패를 기록 |
| 미확인 면적·가격·주소 | `NULL`과 사유 표시; 비교 가능 상태로 취급하지 않음 |
| 확인된 조건에서 거래 0건 | 건수 0, 중앙값 없음; 기간·지역을 임의 확대하지 않음 |
| 면적 하한·상한과 기간 시작일 | 경계값 포함. 기준일 당일·이후 거래는 제외 |
| 취소 거래의 후속 갱신 | 현재 통계에서 제외하고 저장된 과거 비교에는 당시 값과 변경 여부를 구분 |
| 정상 자료 반복 수집 | 업무 중복을 막되 실제 동일 조건의 별개 거래를 보존 |
| 비교 저장 중 오류 | 비교 세트와 포함 거래의 저장을 모두 롤백 |
| 다른 회원의 관심·노트 접근 | 서버에서 소유권을 확인하고 거부 |

위 표는 최종 앱·DB 테스트 계획이며 통과 기록이 아니다. API 파서·페이지·키 제거에 대한 11개 단위 테스트 통과와 구분한다. DB 제약·적재·트랜잭션·권한·마지막 정상 데이터 유지 테스트는 실제 구현 이후 수행한다.
